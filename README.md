# Jay Footwear

A full-stack, responsive ukay-ukay shoe storefront created for PCFDS Task 4. The visual direction is inspired by bold skate/e-commerce layouts while using an original Jay Footwear identity and design.

## Task 4 requirements included

- Separate role-based interfaces: **Admin Management** (`/admin.html`), **Cashier POS** (`/cashier.html`), **Owner/Manager Reports** (`/owner.html`), and the customer storefront
- Admin tables for **Products/Inventory**, **Orders**, **Customers**, **Suppliers**, **Cashier Accounts**, and all user accounts
- Working admin controls to add/edit products, update stock, add/edit suppliers, add/deactivate cashiers, edit customers, create supplier orders, and record deliveries
- At least five sample records in the main Task 4 management tables
- Use-case support for user accounts, product inventory, stock updates, low-stock alerts, supplier orders, delivery recording, customer records, product availability, sales processing, discounts, printable receipts, and printable/CSV reports
- Suppliers are maintained by Admin and do not have direct login access, matching the selected project scope
- Responsive CSS formatting, horizontal table scrolling on small screens, hover states, labels, and status badges
- Original responsive storefront made with HTML, CSS, and JavaScript
- Six product photographs connected through `PRODUCT.image_path`; replace the supplied logo-free placeholders with your own authentic shoe photos before selling
- Browse-only customer availability display; in-store purchases are intentionally processed through the Cashier POS rather than a misleading storefront bag
- Store location section: Champaca Street, Brgy. Poblacion, Polomolok, in front of L.A. Sari-Sari Store
- Custom 404 page and clearer empty, error, success, and confirmation states
- Sign-in and sign-up pop-up
- Real server-side accounts, bcrypt password hashing, sessions, SQLite storage, rate limiting, and admin-only store records
- Optional verified Google sign-in
- A normalized relational database implementation connected to the supplied ERD: Role, User Account, Customer, Customer Address, Supplier, Supplier Address, Category, Brand, Product Condition, Shoe Size, Payment Method, Product, Product Variant, Inventory, Sales Transaction, Sales Item, Payment, Purchase Order, and Purchase Order Item

## Use-case diagram implementation

- **Administrator:** manage user records, products, inventory, supplier orders, deliveries, customers, and low-stock alerts.
- **Cashier:** log in/out, view availability, process sales, apply discounts, and issue receipts.
- **Owner/Manager:** log in/out, review performance, generate reports, and print/export reports.
- **Customer:** create an account, log in/out, view product details, add available pairs to an order, enter shipping information, select payment, and place an order.
- **Supplier:** stored and managed as an external business entity; Admin handles supplier orders and records deliveries because this project intentionally has no supplier portal.

## Database and ERD

The supplied Oracle ERD has been implemented in SQLite for a portable school prototype. Oracle `NUMBER`, `VARCHAR2`, and `TIMESTAMP` types are represented using SQLite `INTEGER`/`REAL`, `TEXT`, and timestamp text values. Primary keys, foreign keys, unique constraints, checks, and normalized relationships are retained. Product cards and all management tables are generated by SQL joins across these normalized tables—not hard-coded in HTML.

## Run locally

1. Install Node.js 20 or newer.
2. Open a terminal in this folder.
3. Run:

```bash
npm install
cp .env.example .env
npm start
```

4. Open `http://localhost:3000`—do not open `index.html` directly and do not use VS Code Live Server.

On Windows PowerShell, if scripts are blocked, use:

```powershell
npm.cmd install
Copy-Item .env.example .env
npm.cmd start
```

## Enable Google sign-in

Google sign-in requires your own Google Cloud credentials; no application can safely include somebody else's credentials.

1. Go to Google Cloud Console → APIs & Services → Credentials.
2. Configure the OAuth consent screen.
3. Create an **OAuth client ID** of type **Web application**.
4. Add `http://localhost:3000` and your deployed HTTPS site URL as Authorized JavaScript origins.
5. Copy the client ID into `.env`:

```env
GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
```

6. Restart the server. The Google button appears automatically.

## Important deployment notes

- Replace `SESSION_SECRET` with a long random value.
- Use HTTPS and set `NODE_ENV=production`.
- The default in-memory session store is suitable for a school/local prototype. For multi-instance production deployment, switch to a persistent session store.
- The storefront is browse-only by design; sales and receipts are processed through the Cashier POS. The newsletter form remains a front-end prototype.
